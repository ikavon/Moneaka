# 事故记录：DPO 用了错误的合并基座

日期：2026-10-23
影响范围：`docs/STAGE3_DPO.md` 里的**全部** dpo-a/b/c/d 结果作废。

## 经过

阶段 A 跑完四组 DPO，按写死的验收线（sem ↑、win ≥0.40、契约 100%）判定
**dpo-b 与 dpo-d 通过**，当时得出的结论是「DPO 治住了语义漂移，风格代价在噪声内」。

用户要求「不看指标，只看输出」。把 206 条按语义分档摊开后人眼一看就发现：

1. 大量 `笑 → 微笑`、`开心 → 微笑` 的标签替换（21 + 14 例）
2. 单段指令直接丢标签、多段指令自己加标签
3. 一句话里掺 `worth it`

于是回头量真正的硬指标——**标签序列严格遵从率**：

| 模型 | 序列完全一致 | 逐位标签准确 |
|---|---|---|
| run8（SFT） | **204/206 = 99.0%** | 542/542 = 100% |
| dpo-a | 142/206 = 68.9% | 88.4% |
| dpo-b | 142/206 = 68.9% | 89.3% |
| dpo-c | 147/206 = 71.4% | 90.8% |
| dpo-d | 142/206 = 68.9% | 88.9% |

看起来像是「四组 DPO 把核心硬指标打崩了 30 个百分点」，而且四组超参差那么多，
遵从率却撞在同一个数上（69/69/71/69）——这个「太整齐」本身就是线索。

**后续更正：DPO 没有打崩标签，它只是继承了坏基座。** 旧合并产物来自 run2，
而 run2 自己的标签序列遵从率就是 **62.8%**（`full_run2`，226 条官方样本）。
换句话说 DPO 把一个 63% 的模型训成了 69%，是**小修小补**，不是破坏。
我一开始把因果归错了，记在这里。

## 根因

`tools/train_dpo.py::merge_sft()` 里写着：

```python
if (Path(tgt) / "config.json").exists():
    print(f"合并基座已存在: {tgt}")
    return tgt
```

而 `data/models/Qwen3-1.7B-sft-merged` 是**前一天 17:26** 建的，内容是用 **run2**
合出来的旧货。所以四组 DPO 的 policy 初始化和 ref 模型都是 run2 合并版，
不是 run8。

确认方法（可复现）：取 `model.layers.0.self_attn.q_proj`，
把 `merged - base` 和每个 adapter 的 `B@A` 做最小二乘拟合 —— 谁的尺度接近
`alpha/r`、相关最高，就是谁合出来的：

| adapter | 拟合尺度（期望 2.0） | 相关 |
|---|---|---|
| **run2** | **1.988** | **0.966** |
| run8 | 0.173 | 0.135 |
| run7 | 0.139 | 0.127 |
| 其他 | 0.01~0.75 | ≤0.44 |

## 为什么没被拦住（三个漏洞）

1. **缓存无来源标记**：只看目录存在。同名目录被别的实验复用，静默返回。
2. **「契约 100%」是假绿灯**：`contract.check()` 只验证**格式**（有没有 `语气:` 行、
   段数对不对、标签在不在白名单），不验证**标签序列是否照指令执行**。
   序列遵从率是另一个工具 `tools/tag_compliance.py`，而 `run_dpo_phase.py` 没调它。
3. **只报均值不摊输出**：自动评委给出 win/sem 两个数就下结论，
   没有任何一步要求人眼看样本。而这次的问题在均值上只表现为「win 掉了 0.04」。

## 修复

1. `merge_sft()` 增加 `.merge_source.json` 标记（记录 base/adapter/时间戳），
   来源不符**直接报错**而不是复用。
2. `merge_sft()` 增加**合并自检**：合完立刻算一层 q_proj 的尺度与相关系数，
   相关 <0.9 或尺度偏离 >20% 中止。（本次修复后实测：尺度 1.998，相关 0.986 ✓）
3. `run_dpo_phase.py` 的验收闸门加入 `标签序列遵从 ≥99%`，并调用
   `tag_compliance.py --json-out` 落盘。
4. `tools/show_outputs.py` 新增：按语义分档摊开 `指令 → 输出 → 真货`，
   **以后每训完一版，先看 10 条输出再谈指标**。

## 重跑结果

修好基座后重训 dpo-b / dpo-d，三个指标全落在噪声里（sem 3.59→3.55/3.57，
win 0.447→0.405/0.432），标签遵从 99.0%→98.5%/98.1%。详见 `docs/STAGE3_DPO.md`。
**结论：这两组 DPO 无效，不启用；当前最优仍是 run8 SFT。**

`docs/DISTILL_PILOT.md` 的对照已用正确基座的输出重测：**0.650，CI [0.50, 0.78]**
（原先用坏基座的 dpo-b 测是 0.600），结论方向不变。
* 旧的四个 adapter 移到 `data/adapters/_stale_run2base/` 留档，不删（便于复盘）。

## 教训

指标失败会自己暴露（win 掉了、sem 掉了），但**格式遵从度的崩溃不会**——
它只会在你看输出的时候跳出来。所以：**训练完的第一件事是看输出，不是看分数。**
